# Фронтенд: канвас с генерацией изображений

React + TypeScript + Vite + `@xyflow/react` (React Flow 12), workspace `@canvas/web`. Других библиотек нет.

## Запуск

Из корня репозитория (Node 24.x, npm 11.x):

```sh
npm ci            # зависимости всех workspace
npm run dev       # API на http://127.0.0.1:4001
npm run dev:web   # фронтенд на http://localhost:5173 (в отдельном терминале)
```

Сборка и просмотр продакшен-сборки:

```sh
npm run build:web     # tsc + vite build → apps/web/dist
npm run preview:web   # раздаёт собранный фронтенд
```

Адрес API по умолчанию — `http://127.0.0.1:4001`; переопределяется переменной `VITE_API_ORIGIN`. Debounce и интервал опроса приходят из `GET /api/config`.

## Как устроена работа с API

Весь транспорт — в двух файлах; компоненты не видят `fetch`, `response.ok`, `response.json()` и `try/catch`:

- **`src/api/http.ts`** — единственная точка отправки (`send<T>` → `{ data, etag }`, и обёртка `request<T>` без ETag). Владеет адресом, заголовками (`Content-Type`, `Idempotency-Key`, `If-Match`), сериализацией тела, кодами ответа, пустыми телами (204/304) и приведением любой неудачи к одному типу `ApiFailure` (`kind: network | http | parse | state`, `status`, `code`, `message`, `retryable`). ETag читается из заголовка здесь и нигде больше.
- **`src/api/endpoints.ts`** — декларации операций: путь, метод, тело, тип результата.

Обобщённые хуки — единственные реализации своих паттернов: `useQuery` (загрузка/ошибка/reload, защита от устаревших ответов), `useAction` (занятость, защита от двойного нажатия, перехват ошибки), `usePolling` (опрос до терминального статуса, остановка при размонтировании, продолжение после восстановимых сбоев), `useIdempotencyKey` (ключ, привязанный к «смыслу» запуска). Отображение: `Async`, `Notice`, `Button`, `SaveIndicator`.

## Debounce и очередь сохранений (`src/graph/useGraphSync.ts`)

Постоянные данные отделены от React Flow: единственный сериализатор `buildGraph` (`src/graph/serialize.ts`) строит канонический снимок `{ nodes, edges, viewport }` без служебных полей RF (`selected`, `dragging`, `measured`), с фиксированным порядком ключей — поэтому два снимка сравниваются побайтово через `JSON.stringify`.

- Любое значимое изменение (позиция, текст, связь, viewport) вызывает `markDirty()`: интерфейс уже обновлён локально, а таймер debounce (500 мс из конфига) перезапускается. Изменения выделения и измеренных размеров снимок не меняют и сохранение не запускают.
- По истечении паузы `drain()` сериализует **текущее** состояние и сравнивает со снимком последнего сохранения: совпало — PUT не нужен. Иначе PUT с `If-Match: <ETag последнего ответа>`; новый ETag берётся из ответа.
- **Очередь длиной один**: пока PUT в полёте, правки только копятся локально; после ответа цикл сохраняет последнее состояние. Из ответа PUT берётся только ETag, тело никогда не пишется в локальное состояние — старый ответ физически не может затереть новые правки. Если пользователь ещё печатает (стоит таймер), цикл уступает debounce.
- **Потерянный ответ PUT** (сбой сети): граф перечитывается и сравнивается с отправленным снимком. Совпал — запись дошла, принимаем ETag и продолжаем; не совпал — одна автоматическая повторная попытка с перечитанным ETag, дальше статус «Ошибка» с ручным повтором. Правки при этом не теряются.
- **412 (конфликт версий)**: локальный черновик остаётся на канвасе, показывается «Граф изменён в другом месте» с кнопкой «Загрузить серверную версию»; слияния нет по условию задачи.
- Перед генерацией `flush()`: сброс таймера, ожидание текущего PUT, немедленное сохранение остатка. Без успешного сохранения генерация не запускается.

## Генерация

Кнопка в ноде генератора: `flush()` → `POST /generations` с `Idempotency-Key` и `{ nodeId, graphETag, scenario }`. Scope ключа — `последняя генерация + ETag + сценарий`: повтор после сбоя сети уходит с прежним ключом, новый запуск получает новый. Опрос статуса живёт в самой ноде генератора (`usePolling` с `pollIntervalMs` из конфига), поэтому удаление ноды или уход со страницы останавливают его автоматически; после перезагрузки список генераций строит карту «генератор → последняя генерация», и `processing` продолжает опрашиваться.

Изображение не хранится в данных нод: карта «resultNodeId → генерация» выводится из карты по генераторам, и нода результата рисует только свою запись. Старый результат не может попасть в чужую ноду, а более новый запуск вытесняет прежний по ключу генератора. `failed` в 200-ответе — состояние (`SIMULATED_FAILURE`), показывается в генераторе и результате с возможностью повтора.

## Разбор горячего участка обработки графа

`isValidConnection` в `src/canvas/CanvasApp.tsx` — React Flow зовёт его непрерывно, пока пользователь тянет связь (каждый кадр наведения). Наивная реализация обходила бы `nodes` и `edges` на каждый вызов: O(N+E) на кадр плюс промежуточные массивы от `.filter()`. Вместо этого две структуры строятся **один раз на изменение** графа: `nodeKindById` (`Map`, один проход по нодам) и `occupiedPorts` (два `Set`, один проход по связям) — обе в `useMemo`, ссылки стабильны между рендерами. Сама проверка — несколько `Map.get`/`Set.has` за O(1) без аллокаций. Сериализация снимка тоже не зависит от частоты событий: во время перетаскивания выполняется только сброс таймера, а `buildGraph` (один проход по нодам + один по связям, ≤20 элементов) вызывается лишь на границах PUT.

## Проверенные сценарии

- Создание пространства при первом входе; после перезагрузки открывается то же пространство (id в localStorage), при `data:reset` создаётся новое.
- Добавление трёх типов нод (лимит 20 отключает кнопки), перемещение, удаление вместе со связями (Backspace/Delete), ввод текста без перетаскивания ноды (`nodrag`).
- Связи только «текст → генератор» и «генератор → результат»; второй вход, второй выход генератора и связь «текст → результат» отвергаются при перетаскивании; id связей — UUID.
- Автосохранение: серия правок → один PUT после паузы 500 мс; статусы «будут сохранены… / сохранение… / сохранены»; viewport сохраняется и восстанавливается.
- Конфликт: правка графа снаружи (curl) + локальная правка → 412 → баннер конфликта, правки не потеряны, «Загрузить серверную версию» приводит канвас к серверному графу и чинит ETag.
- Генерация: успех (картинка в связанном результате), тестовый отказ (`SIMULATED_FAILURE` + повтор), повтор после отказа.
- Перезагрузка во время генерации: граф и результаты восстановлены, `processing` дожат опросом до картинки; опрос останавливается по завершении и при размонтировании.
- Двойное нажатие «Сгенерировать» блокируется занятостью действия.

## Известные недоработки

- Мобильная раскладка канваса не делалась (по условию — только 1280 px).
- Выбранный в генераторе сценарий (успех/отказ) не переживает перезагрузку — это тестовый переключатель, не данные графа.
- При конфликте нет слияния версий (по условию не требуется): выбор — оставить локальный черновик несохранённым или взять серверную версию.
